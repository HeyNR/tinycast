# Drag-to-snap in Loop, Rectangle, and Tinycast

## Recommendation

Use **Rectangle as the behavioral reference**. Its MIT-licensed edge classifier is the strongest candidate for a small source adaptation. Its mouse-down identity and release-time checks also address real drag-tracking problems that Tinycast would need to handle. Keep the monitor, preview, and commit in Tinycast so drag-to-snap shares the existing display geometry, gap rules, restore memory, and window writer. Loop is a useful second reference for how to observe mouse events and show a click-through preview. Its complete drag path carries more dependencies and relies on private SkyLight for its primary hit test. [Rectangle edge detector][rectangle-edges] · [Rectangle drag lifecycle][rectangle-drag] · [Loop hit testing][loop-hit] · [Tinycast window-management invariants][tinycast-geometry]

This is a source review of [Rectangle `0698b04`][rectangle-revision] and [Loop `573ace3`][loop-revision]. Permission behavior, drag timing, and interaction with native tiling remain untested on macOS 26 and 27.

## Rectangle

- **Monitoring and target identity.** The passive path pairs local and global `NSEvent` monitors. Both leave events alone. Its mask includes mouse down, drag, up, and key down for Escape. When configured to suppress Mission Control’s top-edge drag, Rectangle switches to an active session tap that can adjust the event position. Mouse down captures the original cursor and the event’s handling-window ID so later processing can stay tied to the original window. Lookup uses WindowServer metadata and AX, with bounded retries. The lookup includes a private `_AXUIElementGetWindow` bridge and a Stage Manager path that depends on undocumented preferences and the WindowManager AX hierarchy. [Monitor selection and filter][rectangle-monitor-selection] · [Event monitors][rectangle-monitors] · [Target lookup][rectangle-hit] · [AX bridge][rectangle-private] · [Stage Manager lookup][rectangle-stage]
- **Detecting and completing a drag.** Rectangle compares initial and current geometry from the same source, preferring WindowServer frames when it has both and otherwise using AX. A change in size with two edges held identifies a resize. Once a move is established, the pointer selects a snap zone. Mouse-up re-evaluates the zone at the release event’s position, so crossing displays or withdrawing from an edge immediately before release does not commit a stale preview. It can also snap a fast release that never drew a preview when it can prove movement without resize. Rectangle has targeted tests for the edge classifier and frame comparison. [Movement classifier][rectangle-movement] · [Mouse-down, drag and release handling][rectangle-drag] · [Edge tests][rectangle-edge-tests] · [Movement tests][rectangle-movement-tests]
- **Overlay and geometry.** `FootprintWindow` is a transparent, borderless AppKit window that ignores clicks. Rectangle recreates it on a new target display to avoid retaining the old display’s Space. The preview has optional blur, animation, and ordering below the dragged window. Its frame comes from the action calculator, adjusted visible frame, and gap rules. The drop sends the captured window and destination screen into Rectangle’s action pipeline, which owns its own placement, animation, and history. The edge classifier is separable from all of this. It handles corners first and, when early snapping is enabled, keeps the narrower margin along the shared portions of adjacent displays. Its Y axis points up, so an adaptation must translate the comparisons into Tinycast’s AX space. [Footprint window][rectangle-footprint] · [Preview and placement calculation][rectangle-preview] · [Action dispatch][rectangle-action] · [Edge classifier][rectangle-edges] · [Tinycast coordinates][tinycast-coordinates]

## Loop

- **Monitoring and target identity.** Loop installs passive `.cgSessionEventTap` listeners for left drag and release once Accessibility is available. They use a dedicated run loop thread with tap restart handling. It attempts to resolve the window on the first drag event at the current pointer location and suppresses further attempts after a failed resolution. It tries private SkyLight first, then AX hit testing, then a search through on-screen windows. Even the `Window` model checks SkyLight levels and tags when it validates a candidate. The manager compares changes in the four corners against the starting frame and applies the current action at release if it still observes a move. [Observer and drag flow][loop-drag] · [Passive tap][loop-monitor] · [Tap lifecycle][loop-monitor-lifecycle] · [Window lookup][loop-hit] · [Window validation][loop-window] · [Private hit test][loop-private]
- **Overlay and geometry.** The pointer selects a display and an action from edge bands, with aspect-ratio and previous-zone logic for thirds and two-thirds. A screen-sized, borderless, nonactivating, click-through panel hosts a SwiftUI preview across Spaces. The view model reads `ResizeContext`’s padded target frame, and `WindowEngine` reads that context’s target frame when it performs the resize. Adapting this pipeline would pull in its screen and padding policy, window records, stash state, and asynchronous action execution. On recent macOS, Loop can also change the Dock’s Mission Control top-drag preference. ## Fit with Tinycast

1. **Capture and track the window named by the gesture.** An `AppCore`-owned service can track mouse-down, drag, and release while enabled. A mouse-only, listen-only session tap is a candidate if it works with Tinycast’s existing grant. Tinycast already has listen-only tap code. Apple notes that local AppKit monitors miss events consumed by nested tracking loops such as window dragging, so verify AppKit coverage before relying on it for Tinycast’s own windows. Test tap delivery with Accessibility alone and with Input Monitoring denied on both target OS versions. Keep keyboard events and active filtering out of the initial design. [Tinycast ownership rules][tinycast-agents] · [Tinycast listen-only tap][tinycast-tap] · [Apple on passive taps][apple-passive] · [Apple on AppKit tracking loops][apple-local] · [Apple on tap creation][apple-tap]
2. **Use one identity and one placement.** Capture the original event location and handling-window ID when available. Treat the ID as evidence for selecting a candidate, then confirm the same movable window changed position before showing a preview. Evaluate public AX hit testing within `AXWindowAccess` for external windows, and use AppKit for our own windows. Today `WindowMover` resolves an external target’s focused window and the placement engine picks the host by the window frame. A drag needs a narrow seam for the captured window and explicit destination display under the release pointer. Feed the preview and commit from the same pure placement calculation, with the full display frame for edge detection and the visible frame for placement. Use `AXScreens.AXGeometry` for the display snapshot and retain the existing move, read-back, and history sequence. [Apple AX hit test][apple-hit] · [Apple event window field][apple-window-field] · [Tinycast target and writer][tinycast-mover] · [Tinycast geometry and gap rules][tinycast-coordinates]
3. **Keep the first version small.** A Tinycast-owned click-through, nonactivating panel can display the placement frame and clear on release, cancellation, permission loss, feature disable, or display/Space changes. Confirm an actual window move before treating an edge as a target, then recheck the release event to avoid false snaps on content drags, resize gestures, or a fast exit from a snap zone. Measure how often AX frame sampling is needed before confirmation, since each AX call can block and the current mover documents a one-second messaging timeout. If a later implementation defers any work, validate the gesture identity before showing or committing its result. [Rectangle movement and release][rectangle-drag] · [Loop preview panel][loop-preview] · [Tinycast ownership and cancellation rules][tinycast-agents] · [Tinycast AX write behavior][tinycast-write]
4. **Verify coexistence with macOS.** macOS already tiles on edge, corner, menu-bar, and Option drags. Desktop & Dock exposes native tiling and Mission Control controls. Test with those settings on and off, without changing system preferences in Tinycast. Also check mixed-size displays and shared edges, fullscreen Spaces, Stage Manager, our own AppKit windows, and content drag versus title-bar drag. An explicit trigger or a native-tiling setup instruction is a product decision if unmodified drags otherwise produce two previews or competing placements. [Apple native tiling behavior][apple-tiling] · [Apple tiling settings][apple-tiling-settings] · [Tinycast coordinate and testing notes][tinycast-coordinates]
